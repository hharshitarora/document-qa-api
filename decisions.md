# Decisions

Running log, written as each choice is made. Feeds the README.

| # | Decision | Why | Tradeoff |
|---|---|---|---|
| 1 | Retrieval augmented generation rather than prompting the model on its own | An LLM knows nothing about a customer's internal documents, so the document has to supply the facts and the model only supplies the reasoning and the wording | Answer quality is now capped by retrieval quality: if the right passage is not retrieved, a capable model still cannot answer |
| 2 | LangChain for document loading, splitting and the vector store interface; retrieval, prompting and the answer schema written by hand | The brief suggests LangChain, and its loaders and splitters are commodity work; grounding and the output contract are the parts worth owning | More code than an off-the-shelf chain, and two layers to understand instead of one |
| 3 | Vectors held in memory, behind LangChain's vector store interface | One 84-page document is roughly 300 chunks, so exact search is instant and needs no extra service; the interface means Chroma or pgvector is a one-line swap | Nothing survives a restart, and it does not scale past what fits in memory |
| 4 | Built index cached in memory, keyed by a hash of the uploaded file | Re-uploading the same document skips embedding entirely, saving time and API spend | Cache is lost on restart, and memory grows with distinct documents unless evicted |
| 5 | Chunks of 1200 characters | Their sample is a SOC 2 report, where a self-contained unit is one control description running a paragraph or two; 1200 characters is about 300 tokens, just above that, so a control stays intact | Larger chunks drag neighbouring controls into the prompt and blunt retrieval precision |
| 6 | Overlap of 200 characters | Roughly 15 percent, enough that a sentence straddling a split still appears complete in one of the two chunks | Some text is embedded twice, a small cost in tokens and storage |
| 7 | Retrieve 5 chunks per question | Their questions often span several facts, so the answer can sit across passages; 5 is about 1500 tokens of context, cheap against the budget | Fewer would risk missing a passage, more would bury the answer in nearly relevant text |
| 8 | Split page by page, never joining pages into one text | Keeps the page number exact on every chunk, so a citation points at "page 43" rather than at the document; precision of a citation is capped by the unit kept | A control running across a page boundary gets split with no overlap to rescue it, since overlap only applies within a page |
| 9 | Read the PDF with `pypdf` directly instead of a LangChain loader | The PDF loaders live in `langchain-community`, which is being sunset, and the maintained alternatives each cost something: PyMuPDF is AGPL, Docling downloads models, Unstructured needs system packages. Reading pages directly is a few lines and keeps control of citation metadata | One less framework convenience, and no table-aware parsing: tables flatten into text lines |
| 10 | Collapse runs of whitespace at load time | pypdf preserves layout spacing, so words arrive separated by two or three spaces; measured at 23% of all characters in the sample report, meaning chunks held a quarter less real content and retrieved chunks spent tokens on padding | Visual layout is lost, so table columns run together, though this parser flattens tables regardless |
| 11 | Detect and strip the running page header at load time | The sample report repeats the same title line on all 84 pages, which appeared in 84 of 232 chunks; identical text everywhere adds no information and pulls every chunk towards the same generic meaning | Detection is heuristic: a document whose real content happens to repeat on a third of its pages would lose it |
| 12 | Answer and not-found state carried as separate fields in a structured response, rather than a sentinel string inside free text | A prompt asking for `Data-Not-Found` "if the passages do not contain the answer" produced a correct answer with the sentinel appended to it, so a reader could not tell an answer from a refusal; separate fields make that contradiction unrepresentable instead of merely discouraged | A structured call is stricter and can fail to parse, so it needs its own error path |
| 13 | Citations verified against the passages actually retrieved, and an answer with no surviving citation downgraded to not found | The model can name a page it was never shown or reword a quote; checking both is what separates proven grounding from claimed grounding, and an uncited answer cannot be checked at all | Stricter than the brief requires: a correct answer whose quote was paraphrased loses its snippet, and one whose citations all fail is reported as not found |
| 14 | JSON documents treated as generic JSON, one record to one passage, with no assumption they hold question and answer pairs | The brief promises only that the API accepts JSON and says nothing about its shape, so tuning for the sample file would be fitting to one example | Loses accuracy on a file that really is a question and answer bank, where matching the question field alone would retrieve better |
| 15 | Citation location carried as one string ("page 17", "record 3") rather than a numeric page field | One field covers both file types, so nothing downstream has to know whether the source had pages or records | Less machine-readable than a number, and a caller wanting the page has to parse the string |
| 16 | Partial answers required, taught with a worked example in the prompt | Their questions are multi-part, and refusing a whole question because one clause is uncovered hides facts the document does state; the instruction alone did not change behaviour, the example did | A partial answer can read as overclaiming if the model states the gap weakly |
| 17 | Prompt written as prose, not as a bulleted rule list | Identical instructions as bullets under a "Rules:" heading were refused where prose was answered, twice each at temperature 0, on a borderline question | Harder to scan than a rule list, and the reason lives in a comment rather than being obvious |
| 18 | Dense vector search only for now, hybrid keyword search deferred | Hybrid is the correct fix for the one retrieval miss found, but it is about an hour plus tests and moves one question of five, while the API, error handling, tests, container and UI carry 60 rubric points between them and do not exist yet | One question stays unanswerable that a keyword match would solve; shipped as a documented limitation rather than a silence |
| 19 | Uploads parsed in memory, never spooled to a temporary file | Document text is customer compliance data, and the service promises not to write it to disk; a temp file would quietly break that promise and add cleanup and permissions to worry about | A very large upload is held in memory, so the size limit matters more than it would with a temp file |
| 20 | One set of parsers shared by the API and the command line, taking a stream or bytes rather than a path | The CLI and the endpoint cannot drift apart if there is only one code path, and it is the difference a reviewer checks when a repo has both | Slightly more indirection: `load` and `load_bytes` both delegate rather than each doing the work |
| 21 | Questions file accepted as a bare JSON list or as `{"questions": [...]}`, with items as strings or objects carrying a `question` field | The brief says only "a file containing a list of questions", so tolerating both shapes avoids failing a reviewer who sends the other one | Accepting several shapes means silently ignoring malformed items, which needs explicit validation next |
| 22 | Per-question errors rather than failing the whole request | A questionnaire of 50 questions should not be lost to one failed call; the caller gets every answer that worked plus a message on the one that did not | Callers must check both `found` and `error`, and a partly failed batch still returns HTTP 200 |
| 23 | Concurrency capped by a semaphore at 5 questions in flight | Unbounded fan-out on a 200-question questionnaire would trip rate limits and spend faster than it answers; 20 questions measured at 7.1s, 0.36s each, against roughly 1.2s each in sequence | A slow question holds a slot, so one straggler can delay the batch |
| 24 | Retries left to the OpenAI client, not written by hand | The client already retries rate limits and transient failures with backoff; a second retry layer would multiply attempts and hide the real error | Less control over the policy, and the timeout is per attempt rather than per question |
| 25 | Two error types, `InputError` mapped to 400 (413 when too large) and `UpstreamError` to 502 | Status-code decisions stay in the HTTP layer while the pipeline just says whose fault a failure is, and library exceptions never reach a response as a stack trace | Every library call site has to translate its exceptions, which is a little ceremony in the loaders |
| 26 | Document cache checked **before** parsing, in a pipeline module of its own | Caching only the embeddings saved nothing measurable: repeat requests stayed at about 11s because PDF parsing is the slower half. Hashing the bytes first and skipping parse and embed took a repeat request from 12.3s to 2.4s | A separate module for a small amount of state, and the API now reports a `cached` flag it must keep honest |
| 27 | Tests run entirely offline with the model and embeddings faked | A suite that calls OpenAI is slow, costs money, and fails for reasons unrelated to the code; 61 tests run in about a second and give the same result every time | Faking `with_structured_output(..., include_raw=True)` means imitating its dict shape, so the fake is coupled to that API |
| 28 | Answer quality checked by a separate script, `scripts/eval.py`, not by pytest | Judging grounding needs real model calls against a real document, which does not belong in an offline suite; as a script it can be run when the prompt or retrieval settings change | It is only run by hand, so a regression in answer quality is not caught automatically |
| 29 | The eval published at 7 of 9 rather than tuned until green | The two failures are real and diagnosed, and a script tuned to pass tells a reviewer nothing; it is also the evidence for hybrid retrieval being the next step | The headline number looks worse than a curated one would |
| 30 | Logs as one JSON object per line on stdout, using the standard library | That is what a container platform collects and what a log aggregator parses, and a small formatter avoids adding a logging dependency for it | Less convenient than a library like structlog for context binding, and the formatter is ours to maintain |
| 31 | Logs carry counts, timings and identifiers only, never document or question text | Documents are customer compliance data, so logs stay safe to ship to a third-party aggregator; a request id in the response header is enough to trace a reported problem | Debugging a bad answer from logs alone is not possible, it needs the document re-run locally |
| 32 | Estimated spend logged per request from token counts | Makes cost visible per request rather than discovered on a bill, which matters when a key has a $5 ceiling | Rates are hardcoded, so they go stale when pricing changes; it is an estimate, not billing |
| 33 | `python:3.11-slim` with a non-root user, dependencies in their own layer | Matches the local interpreter, keeps the image small without compiling wheels as alpine would, and nothing in the service needs root | Slim still carries glibc and a shell, so it is larger than a distroless image |
| 34 | Key passed in at run time, never baked into the image, and `.dockerignore` excludes `.env` | An image is copied and shared; a key inside one leaks with it | Running the container needs the environment variable supplied, which is one more step for a reviewer |
| 35 | Minimal page as one static HTML file with no framework or build step | Their rubric wants an upload and results view with polish not required, and a single file means no toolchain between a reviewer and a working page | No component structure, so it would not grow well into a real front end |
| 36 | Every dependency pinned explicitly, including ones that arrive transitively | `numpy` was absent from requirements and the service worked locally because another package had pulled it in; the first clean container build failed every retrieval. A dependency that is not named is not a dependency you have | The list is longer and has to be maintained by hand when versions move |
| 37 | The prompt distinguishes a control from a fact: a passage describing a policy, control or auditor test proves the control exists, not that the activity happens | An independent review found the system answering "Yes, personal information is transmitted to third parties" from a passage about vendor risk assessment. The citation was accurate and the conclusion was not supported. For a questionnaire tool that failure is worse than a refusal, because a confident Yes gets pasted into a real security assessment | Stricter, so a question whose answer really is implied by a control now declines; the eval carries two cases pinning this behaviour |
| 38 | Answer-quality eval published at 9 of 11, with the two failures kept as visible cases | Both remaining failures are retrieval misses with a known cause and a known fix; hiding them by deleting the cases would make the number meaningless | The headline number stays below full marks in a graded submission |

Starting points, to be checked in Phase 4 against what actually gets retrieved for their 5 questions.

## Notes
- The brief's link to LangChain's question-answering tutorial now redirects to their Deep Agents RAG page. Built the plain retrieval pipeline the brief describes, not the agent framework.
- Deliberately not persisting document text to disk: this is customer compliance data, and storing it would raise retention and deletion questions a take-home should not create.
